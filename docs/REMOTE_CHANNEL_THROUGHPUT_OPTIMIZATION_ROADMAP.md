```text
录像唯一身份速率 = 643 / (60.4 + 1/60) = 10.642758620689655 /s
普通帧数据预算 = 14 × 1,314 = 18,396 B
数量级上限 = 10.642758620689655 × 18,396 ≈ 195,784 B/s
人工 30 Hz 观察 = 40,517,389 / 210 ≈ 192,940 B/s
```

## 2. 优化边界与评价规则

### 2.1 已由用户确认的选择

1. **允许修改整个项目，不要求新旧版本互通。** 旧版本保留为可复现对照；具体新协议尚未冻结。

### 2.2 持续保留的工程约束

- 生产 Decoder 的 payload 只能来自实际捕获的视觉输入，不增加网络、剪贴板、共享内存、源文件交换或其他旁路，不增加隐式 ACK。测试 oracle、人工回传报告与生产 admission 隔离。

- 内存保持 `O(active segment set)` 和有界队列／包缓存，不以扩大活跃解码器或 orphan 配额掩盖问题。统计溢出和覆盖缺失必须显式报告。
- 源文件在 Session 内不可变；编码字节、方程身份和 descriptor 不可因 Carousel 重复而漂移；零字节、DirectRepeat、短尾段等边界继续覆盖。
- 保持 Qt-free 核心、D3D11 cross-vendor 基线、单 immediate-context owner 与安全 GPU lease；不为追求 FPS 增加隐式 GPU→CPU→GPU 往返。
- 本机实屏仅用右屏，不激活窗口抢焦点、不注入输入、不改变左屏、显示设置或鼠标／键盘行为。每次先检查保护屏与测试屏拓扑，失败即停止。

- 启动、就绪、首次观察、控制获取、首个有效方程、payload 完成、摘要、发布、重开分别记录。比较前冻结主计时起止点，不事后减去丢帧、控制等待或恢复尾部。

**待验证假设：** 可以通过分阶段观测解释现有有效吞吐，而不是将全部损失归因于模糊或低刷新率。

**改动范围／接口变化：** Sender／Decoder 诊断字段、受限采样、独立 Unified 录像回放入口；生产 payload 输入保持不变。详细报告 schema 在此 Step 计划中确定。

**实施内容：**

- Sender 分开测量 Outer 生成、Inner 编码、raster、全屏合成／拷贝、Submit 等待和实际呈现。
- Decoder 分开测量捕获、重复观察、Bootstrap、区域 freshness、各 lane FEC／CRC、新方程、重复方程、资源延后与最终存储。
- 建立 Unified 录像回放工具，按原始 PTS 流式读取像素，复用生产解调与 Receiver；不能未经核对就宣称旧 Profile 工具支持 Unified。
- 对当前录像输出逐 lane／逐阶段统计；60 秒不足以完成整文件时仅报告诊断和部分恢复。
- oracle 与生产解码器隔离，仅在能重建精确发送编码字节时比较 accepted payload 真值，否则记为 unavailable。
- 诊断输出按时长、帧数、字节数封顶；默认不开持续全分辨率 GPU readback。采样覆盖不足不得被伪装成完整运行统计。

**最小测试：** PTS／重复／截断输入、硬上限与错误退出、当前 Profile 路由、生产接纳集合一致性；使用小输入完成一条闭环，不默认重跑整个 GPU 矩阵。

**产物／退出条件：** 可重放诊断报告、损失分解与瓶颈排序；解码器不接收源文件、期望 payload 或预知方程。当前录像的不完整恢复不自动等于工具失败。

**未通过处理：** 回到最早不确定的输入／身份／时间环节；不能通过放宽质量门、FEC 或时效门让回放看起来更好。

### Step3 — 建立受实测约束的离线信道测试平台

**2026-09-08 增量：** 已单独获准完成 Step3-A：4 张生产封存像素、9 个固定时序／变换场景、软件 WARP 原恢复入口、两轮 76 观察精确重复及 512 B 小文件闭环。已知几何失败仍拒绝发布，不改准入；未执行有状态码率约束 codec、现场校准或多帧／大文件恢复证明。见 [执行记录](REMOTE_STEP3A_EXECUTION_2026-09-08.md) 和[独立工具](../tools/PBRemoteThroughputStep3A/README.md)。以下完整 Step3 目标没有因此全部完成。

**2026-09-08 后续独立获准的 Step3-B 增量：** 一个64 KiB多帧文件、30张生产封存像素、15fps/2秒；软件libx264 High4.0/yuv420p/limited BT709 left，8Mbit/s、VBV4Mbit、closed GOP15。原始前三帧已进入Outer但未恢复，完整原始对照通过整文件摘要、安全发布、reopen和外部双摘要。首个错误颜色码流保留并经用户确认补齐元数据后，两次正式codec重建逐字节一致、属性检查通过，但原生产几何门拒绝全部30帧，均NOT_RECOVERED；未到达的数据阶段为null，不改准入。正常观察93/93，未扩展参数矩阵／压力／实屏。见[Step3-B执行记录](REMOTE_STEP3B_EXECUTION_2026-09-08.md)及[工具说明](../tools/PBRemoteThroughputStep3B/README.md)。最小本地诊断完成不代表codec恢复或完整Step3通过，现场校准与Holdout仍未完成。

**目标：** 白天筛掉多数无效方案，晚间仅验证少数关键假设。

**前置条件：** Step2 的像素输入、时序解释与诊断路径可复现。

**待验证假设：** 有状态、受码率约束并以实测轨迹校准的离线测试，比独立图片模糊更能筛选有效候选；其预测能力仍需现场检验。

**改动范围／接口变化：** 复用 simulator，增加确定性时序／码流测试清单、工具参数与证据报告；不增加产品隐藏媒体或源文件输入。

**实施内容：**

1. 真实录像回放：用于现有解码器 A/B 和损失统计。
2. 确定性失真：覆盖缩放相位、色度中和、4:2:0、模糊、量化、遮挡、区域延迟、混帧、重复和突发丢帧。
3. 有状态视频压缩：新视觉序列经固定 FFmpeg 编码／解码，加入码率约束、GOP 与时间采样，再进入恢复链路。

- 不能仅对独立图片做 blur，也不能只用不受码率约束的 CRF 推测拥塞远控。记录实际码流参数、PTS、颜色空间与输出码率。[FFmpeg 文档](https://ffmpeg.org/ffmpeg-codecs.html)
- 按独立录制批次划分 Train／Validation／Holdout，不随机拆分同一录像的相邻重复帧；当前录像只作诊断／开发资料。
- 区分模拟信道时间与实际计算耗时，不把离线高速处理当作信道加速。
- 旧录像不能证明尚未发送的新波形更好；新布局必须生成自己的序列，并最终取得新的真实资料。

**最小测试：** 确定性重建、清单／种子／PTS／颜色与码率核对、受限输出、codec 失败处理、已知混合／丢失负例，以及小型全文件离线闭环。

**产物／退出条件：** 可重建测试集、固定参数清单和离线恢复证据；始终注明不能替代 Citrix 实测。

**未通过处理：** 模拟与新现场资料不符时修正模型并重新筛选；不通过挑选有利失真参数或污染 Holdout 维持原结论。

### Step4 — 先优化现有实现与发送节奏

**目标：** 不改变视觉合同，取得低风险收益并建立更强对照。

**前置条件：** Step2 瓶颈诊断与 Step3 筛选能力就绪；Step1 的现场测量工具已准备。

**待验证假设：** 当前产帧／提交路径或节奏存在可降低的额外成本；提高 Submit FPS 不一定提高最终吞吐。

**改动范围／接口变化：** 内部计算、缓存、拷贝和有界流水线；研究节奏参数仅用于试验。保持 wire、Profile、Golden 与生产准入语义不变。

**实施内容：**

- 现有代码已有绝对逻辑时钟，先测 CPU 编码、逐像素 raster、全屏拷贝及呈现背压，不能直接假定需要重写时钟。
- 仅对已确认热点尝试固定映射查表、glyph／颜色块预计算、减少重复地址计算和整帧拷贝。
- 保持有界流水线和资源所有权，不通过积压后突发补帧制造提交 FPS。
- 初轮比较 `5 / 10 / 15 / 30 Hz`，仅在胜出区间增加相邻采样，不展开完整 1–60 Hz 矩阵。
- 增加静态驻留／连续变化短探针，实测停留后是否改善画质，不预设 Citrix 必然自动变清晰；该行为取决于实际模式。[Thinwire 与 Build to lossless](https://docs.citrix.com/en-us/citrix-daas/graphics/thinwire.html)

**最小测试：** 受影响时钟／raster／提交测试、Golden 字节一致性与有界资源检查；实机集中在检查点 A。

**产物／退出条件：** 最佳现有格式配置及测量支持的优化。若完成时间无改善，更高提交 FPS 只能是诊断结果。

**未通过处理：** 保留负结果与原对照，不晋级无净收益改动；若瓶颈在链路，转向后续结构实验而非无限优化 CPU。

### Step5 — 单独验证空白区的控制与修复增益

**目标：** 以小范围实验核实截图建议的收益及遮挡边界。

**前置条件：** Step4 对照配置可用，Step3 能做独立 A/B；开始前明确新实验身份与控制恢复策略。

**待验证假设：** 空白区承载短控制／修复块，可能比按现有码字直接补数据更有效。

**改动范围／接口变化：** 实验 region manifest、独立短块及其身份／校验、控制调度；这些是候选合同变更，不默默覆盖现有 layout 10。

**实施内容：**

- 保护既有定位、Bootstrap、校准和 guard，仅在两块空白带内试验。
- 每块保守按 608×64 估算，两块共 77,824 pixels，占画布约 3.75%；按 6×6 排列增加约 2,020 个单元。
- 当前 Luma/Chroma 未用位数分别为 5,488 / 2,744；加入新单元后分别为 13,568 / 6,784，均少于 16,200-bit 码字。因此不能直接推导多出完整码字或按面积计算 payload 增益。
- 优先比较独立短 FEC 控制块（重复当前段描述符）与自包含的小型补充修复块。
- 基础区保留周期性完整控制。离线及现场证明可靠后，才减少普通帧的一整个描述符码字占用。
- 上下区域独立校验；右上角、左下角及两者完全遮挡均不能破坏基础恢复。

**最小测试：** region／guard 不重叠、短块损坏／冲突／资源边界、两区域分别与同时遮挡、控制丢失后重新获取、小文件基础恢复及独立 A/B。

**产物／退出条件：** 容量账本、遮挡证据与实测增益；释放一个普通帧控制码字的理想载荷增益为 `15/14−1 ≈ 7.14%`，实际须扣新开销，不承诺数倍提速。

**未通过处理：** 无增益或遮挡破坏恢复则不晋级；保留可复用的实验结果，不削弱基础控制要求。

### Step6 — 验证独立分区更新，降低全画面同步变化压力

**目标：** 减少整幅高频纹理同步变化，测试能否提高实际送达的新信息量。

**前置条件：** Step5 已记录结论（允许未晋级）；Step3 可用，并已在该 Step 计划中明确独立包与重组身份。

**待验证假设：** 减小一次变化的画面区域并延长局部驻留，可以改善远控交付效率；不是既定事实。

**改动范围／接口变化：** 候选 3×3 面板 manifest、独立包保护头／身份、局部更新调度与有界 Receiver 包状态；不预先指定未经验证的 wire 字节布局。

**实施内容：**

- 首个原型固定 3×3 面板，比较一次更新 `1 / 3 / 9` 个，先保持调制和纠错尽可能一致，隔离更新策略影响。
- 独立包必须明确绑定 Session、Segment、Outer 方程、面板和包序号；保护头损坏或身份有歧义则拒绝。
- 未更新面板的实际像素保持不变，包括局部扰码／置换，不能仅逻辑不变而纹理仍改变。
- 内层码字不跨独立面板；同一 capture 内不同面板可属不同包序号，但各包必须独立完整校验。
- 不把不同全局帧像素拼成旧协议码字，不跨未知身份做软合并；同身份不同有效内容仍是冲突。
- Receiver 使用有界面板／包状态；比较时固定画布并明确新方程预算，不把小面板更新数冒充完整帧数。

该方向借鉴 RDCode 的独立块与局部失效隔离；“分区更新改善 Citrix 吞吐”仍是本项目待验证假设，论文没有提供本链路的性能结论。[RDCode 原论文](https://mashuai-ms.github.io/pubs/mobicom2014.pdf)

**最小测试：** 单面板／多面板更新、像素稳定性、错序／重复／旧头新数据／混合包／冲突、有界缓存与资源不足，以及受码率约束的 A/B。

**产物／退出条件：** CPU 参考原型、新身份合同草案、安全负例与净吞吐证据。检查点 B 的最小实机试验接线只用于候选评估，不提前替换产品默认实现。

**未通过处理：** 无净收益则不晋级；允许保留全帧方案作为后续对照，不因已获重构授权而强行换架构。

### Step7 — 联合搜索压缩友好的调制与局部纠错

**目标：** 优化每单位链路成本能正确传递的字节，而非理论 bits/cell。

**前置条件：** Step6 的更新策略有明确结论，Step3 的数据划分与评分方式已冻结。

**待验证假设：** 更低频／分层符号与适当局部纠错，可能用更低失真或编码成本补偿名义容量减少。

**改动范围／接口变化：** 实验码本、映射、校准、局部 FEC 身份及对应 manifest／Golden；最终参数在该 Step 根据证据冻结。

**实施内容：**

将搜索限制为三个家族：现有 separated shape/chroma 的局部改进；更粗尺度、较低空间频率亮度符号且色度仅为增益；低频基础信息加细节增强信息的分层候选。

- 先筛几何／码本，再筛局部 FEC，最后只验证少数联合配置，不展开所有参数的笛卡尔积。
- 同时评分实际码率、新方程／秒、计算成本与最终文件吞吐；Chroma 完全失效时基础通路仍能恢复整文件。
- 保留 soft QC-LDPC 参考，其他局部纠错候选必须证明净收益，不因易实现就替换。
- 码本、LLR、FEC、映射在查看 Holdout 前冻结。
- 不采用缺少可靠身份保护的时域差分链，避免一次丢帧污染所有后续数据。

libcimbar 可参考符号区分度、有限漂移搜索和纠错开销；Focus 提供不同空间细节层次承载数据的思路。屏幕—相机吞吐不能移植为 Citrix 预测。[libcimbar 技术说明](https://github.com/sz3/libcimbar/blob/master/DETAILS.md)、[Focus 原论文](https://user.it.uu.se/~eding810/conferences/Mobisys16.pdf)

**最小测试：** 固定 Train／Validation／Holdout 重建、码本／映射 Golden、色度失效与局部低通、独立 accepted-payload 真值及小型全文件闭环。

**产物／退出条件：** 评分表、冻结参数、新 Golden 与真值负例；仅保留有净收益的少数候选。

**未通过处理：** 淘汰候选并保留失败资料；不得观察 Holdout 后反复微调再将同一数据称为独立验证。

### Step8 — 优化迟加入、冗余分配与大文件调度

**目标：** 缩短恢复尾部，避免小文件有效而大文件大量方程浪费。

**前置条件：** 候选实际载荷、方程到达和突发丢失轨迹可测量，现有 Receiver 资源边界已核对。

**待验证假设：** 控制获取、冗余／轮转与窗口推进仍存在可消除的浪费，且可在无反馈和既有资源边界内改善。

**改动范围／接口变化：** 无反馈 scheduler 及其诊断／实验参数；若涉及方程或 descriptor 语义，必须单独明确合同与 Golden，不能作为纯调优偷偷修改。

**实施内容：**

- 分开评价首次控制获取、未知段数据损失、重复方程、padding、已完成段重复发送和 active-window 延后。
- 保留 Pass 0 systematic、后续新 repair IDs 语义，以及同段编码字节／descriptor 稳定。
- 用实测到达轨迹与突发丢失选择初始冗余、局部修复、轮转和控制重复，不只按独立随机丢失百分比计算。
- 覆盖 5 段主文件及 9／16 段窗口边界，不能用恰好 8 段的测试证明窗口推进。
- Sender 不知道 Receiver 已完成哪些段，不引入等待接收完成再滑窗的隐式反馈。
- 不以提高活跃段上限、orphan 配额或隐藏 busy 计数消除表面问题。

**最小测试：** 迟加入、周期抽帧、突发停顿、控制缺失、5／9／16 段恢复、修复 ID 稳定与耗尽、资源边界和最终发布；先离线，再将大于 8 段的真实检查留给检查点 D。

**产物／退出条件：** 冻结的无反馈策略与恢复证明；大文件结论和 5 段主文件结论分开。

**未通过处理：** 明确方程损失或窗口阻塞来源；不能用大配额、分母变化或后续偶然恢复伪装成本轮效率通过。

### Step9 — 将胜出方案接入 GPU 与正式双端

**目标：** 确保离线算法收益不被实际计算、捕获或 UI 成本抵消。

**前置条件：** Step5–8 的候选已通过相应晋级门，具体接口／版本身份在该 Step 计划中确定。

**待验证假设：** 候选可在现有跨厂商 D3D11 和有界捕获架构中保留 CPU 参考语义及实际收益。

**改动范围／接口变化：** GPU shader／compact result、生产 Receiver 接线、包／区域报告字段和最小 GUI 配置；新协议使用新 Profile／layout，旧版本仅作对照。

**实施内容：**

- 仅接入晋级候选，保留 CPU oracle；不把被淘汰的全部实验方案塞进产品。
- 新包／区域使用有界调度；失败包可在同身份后续更清晰的观察中重试，不能仅因 Header 重复永久跳过。已接纳身份的内容冲突检查不能被性能捷径绕过。
- 保持单 immediate-context owner、GPU lease 安全与显式背压。
- 新增区域／包唯一量、新方程、时延和不可用原因，不重定义旧 `UniqueVisualFPS`。
- 不要求新旧互通，但保留旧包和证据；不同不兼容 Profile 使用不同 Session。
- GUI 保持简洁，研究参数留在实验 CLI，产品只暴露已冻结、可解释的设置；不按品牌自动切换解码阈值。

**最小测试：** CPU／GPU accepted-byte parity、相关 capture／epoch／shutdown／资源负例、双端受影响目标构建与新解压启动检查；真实右屏仍须单独 opt-in。

**产物／退出条件：** 同身份双端候选、相关报告和安全验证；不把 WARP／GUI smoke 当作实屏性能。

**未通过处理：** 回到最早出现差异的 CPU／GPU／capture 阶段，保留参考路径；不能为了接线成功放宽负例或质量门。

### Step10 — 实机对照、消融与最终冻结

**目标：** 证明完整新产品在目标场景更快，而不是中间计数变好。

**前置条件：** Step9 同身份候选、相关测试、对照包与操作清单就绪；用户本轮确认可用的远程测试窗口。

**待验证假设：** 离线胜出方案在不同迟加入阶段仍有超过基线波动的可重复收益，且可靠性／资源没有明确回退。

**改动范围／接口变化：** 实机测量、对照／消融报告、候选封存和用户说明；不在最终测试现场临时改协议或门槛。

**实施内容：**

- 对照包含原始基线、Step4 最佳现有格式及最终候选，不能只战胜不合适的 Hz。
- 主文件至少三组迟加入对照，覆盖不同加入阶段；交错运行基线和候选，减少随时间变化的网络偏差。
- 对空白区、分区更新、新调制做必要消融，确认收益来源。
- 性能样本先通过整文件摘要、安全发布、final reopen 与外部双摘要；失败和超时样本完整保留，不从报告中移除。
- 单独安排大于 8 段的实际恢复；1 GiB 长测不塞入普通 15–30 分钟窗口。
- 只有收益超过对照自身波动、无明确可靠性／资源回退，才冻结新默认方案。结果接近记为证据不足，不强行宣布提速。
- 若现有格式调优胜出而重构无净收益，允许交付较小改动版本，不以改动规模作为成功标准。

**最小测试：** 检查点 C 的完整文件交错对照、必要消融、检查点 D 的跨窗口／遮挡恢复，以及最终集成检查点的完整相关回归。每晚超额项目顺延，不自动转长时后台。

**产物／退出条件：** 同身份双端候选、完整对照报告、包清单、复现说明及明确限制；未通过实机全文件验证的方案保持实验性。

**未通过处理：** 保留原对照和失败证据，报告无法复现的最早阶段及需要用户配合的事项；没有实测改善则不宣告本优化任务取得提速。
